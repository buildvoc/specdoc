# CNL Parsing & Operations

The **CNL Parsing & Operations** subsystem is the foundational component of the `hedgedoc-nb` engine. Its primary responsibility is to act as a compiler that translates raw, human-readable Controlled Natural Language (CNL) text into a structured, machine-executable sequence of discrete operations, and subsequently transforms those operations into a finalized graph state.

The subsystem is divided into two distinct stages:
1.  **Parsing Stage**: Converts CNL text into an intermediate `CnlOperation[]` array.
2.  **Transformation Stage**: Processes the operation array into a persistent `CnlGraphData` structure via a multi-pass algorithm to ensure referential integrity.

## System Architecture & Data Flow

The subsystem follows a linear pipeline where unstructured text is progressively structured.

```mermaid
graph TD
    A[Raw CNL Text] --> B[getOperationsFromCnl]
    subgraph "Parsing Engine (cnl-parser.ts)"
        B --> B1[Block Separation: Mindmap vs CNL]
        B1 --> B2[Structural Tree Construction]
        B2 --> B3[Node & Morph Extraction]
        B3 --> B4[Neighborhood Scans: Attrs/Rels/Queries]
    end
    B4 --> C[CnlOperation[] Array]
    C --> D[operationsToGraph]
    subgraph "Transformation Engine (operations-to-graph.ts)"
        D --> D1[Pass 1: Node Creation & Basic Morphs]
        D1 --> D2[Pass 2: Morph Augmentation]
        D2 --> D3[Pass 3: Edge/Attribute/Update Linkage]
    end
    D3 --> E[CnlGraphData Object]
```

## Internal Implementation: The Parsing Engine

Implemented in `packages/nodebook-core/src/cnl-parser.ts`, the parsing engine utilizes complex regular expressions to identify structural elements of the CNL syntax.

### 1. Block Separation and Structural Tree Construction
The parser first executes `parseAllBlocks` to partition the input into `mindmap` blocks (using `-` indentation) and standard `cnl` blocks (using `#` headings). For standard blocks, it constructs a structural tree where:
*   `# Heading`: Represents a primary node.
*   `## Morph`: Represents a sub-context or "morph" belonging to the parent node.

### 2. Node Heading Processing
The `processNodeHeading` function parses the primary identifier of a node. It extracts:
*   **Quantifiers**: e.g., `*many*`.
*   **Adjectives**: e.g., `**red**`.
*   **Role/Type**: Extracted from brackets `[...]` (class) or parentheses `(...)` (individual). 
*   **Implicit Edges**: If a heading contains bracketed types like `# Dog [Animal]`, the parser emits an implicit `addRelation` operation (`Dog <is_a> Animal`).

### 3. Neighborhood and Query Scanning
The engine scans the content beneath a node for three specific types of data:
*   **Attributes**: Lines containing `:` (e.g., `mass: 70;`). It handles negation (`!`), units (`*kg*`), and modalities (`[certain]`).
*   **Relations**: Lines wrapped in `<...>` (e.g., `<is_a> Animal;`). It supports weights (e.g., `<inflow> 5 CO2;`) and relation aliasing (e.g., `debit` $\to$ `has post_state`).
*   **Queries**: Specialized Wh-word patterns.
    *   **Node-scoped**: Queries that reference the current node (`<rel> what;`, `<how> Target;`).
    *   **Graph-level**: Queries where the subject is unknown (`who <rel> Target;`, `what: value;`).

## Internal Implementation: The Transformation Engine

Implemented in `packages/nodebook-core/src/operations-to-graph.ts`, this engine implements a **three-pass algorithm** to resolve dependencies between nodes, morphs, and edges.

### Pass 1: Node Creation
The engine iterates through all `addNode` operations. It initializes the `CnlNode` object and automatically generates a "basic" morph for every node. This ensures that even if no explicit morphs are defined, every node has a valid structural anchor (`nbh`).

### Pass 2: Morph Augmentation
The engine processes `addMorph` operations. It locates the existing `nodeId` in the `nodesMap` and appends the new morph context to the node's `morphs` array.

### Pass 3: Linkage and Updates
The final pass processes relations, attributes, and metadata updates:
*   **Relations/Attributes**: The engine attempts to link these to a specific `morphId`. If no `morphId` is provided in the operation, it defaults to linking to the node's "basic" morph.
*   **Negation**: It applies the `negated` flag to edges and attributes based on the presence of the `!` prefix.
*   **Graph-level Directives**: Processes `setCurrency`, `addExpression`, and `updateGraphDescription`.

## Identity Management & Normalization

To ensure deterministic behavior across different input variations, the subsystem implements strict normalization rules via `cnlNameToId` and `singularize`.

1.  **ID Determinism**: Node IDs are generated by lowercasing, removing special characters, and singularizing words. This ensures `# Humans [class]` and `# Human [class]` resolve to the same ID: `human`.
2.  **Singularization Logic**: The parser implements a heuristic-based `singularize` function handling common English patterns (e.g., `-ies` $\to$ `-y`, `-ves` $\to$ `-f`) while respecting invariant words like `species` or `sheep`.
3.  **Role Normalization**: Synonyms for roles are mapped to canonical values:
    *   `concept`, `type`, `universal` $\to$ `class`.
    *   `particular`, `token`, `member` $\to$ `individual`.

## Implementation Constraints

*   **Referential Integrity**: Edges cannot be created for nodes that do not exist in the `operations` array. The transformation engine explicitly skips dangling edges.
*   **Uniqueness**: The first `addNode` operation for a specific ID "wins." Subsequent operations attempting to redefine the same node ID are ignored to prevent state corruption.
*   **Memory/Complexity**: The parsing is $O(N)$ relative to the number of lines, and the transformation is $O(O)$ relative to the number of operations, where $N$ is text length and $O$ is operation count.

## Current Behavior vs. Future Requirements

| Feature | Status | Implementation Detail |
| :--- | :--- | :--- |
| **Node Parsing** | Complete | Supports adjectives, quantifiers, and implicit types. |
| **Morph Support** | Complete | Hierarchical morphs with inherited context. |
| **Attribute Parsing** | Complete | Supports units, modalities, and negation. |
| **Relation Aliasing** | Partial | Only supports a fixed set (e.g., `debit`, `reactant`). |
| **Query Engine** | Partial | Currently limited to Wh-word pattern matching. |
| **Error Handling** | Minimal | Skips malformed operations; does not currently report line-specific syntax errors. |
