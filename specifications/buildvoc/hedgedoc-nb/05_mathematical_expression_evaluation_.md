# Mathematical Expression Evaluation

While [Morphs & Polymorphism](04_morphs___polymorphism_.md) allows nodes to change their context and properties, the **Mathematical Expression Evaluation** subsystem provides the computational logic required to derive new values from existing graph data. It acts as a functional layer that can both evaluate algebraic strings against a numeric scope and decompose complex expressions into structural graph elements (transitions and places) within the Petri net model.

## System Architecture & Data Flow

The subsystem operates in two distinct modes: **Direct Evaluation** (calculating a result from a provided scope) and **Structural Decomposition** (transforming an algebraic expression into a sequence of `CnlOperation` instructions to augment the graph).

```mermaid
graph TD
    subgraph "Mode 1: Direct Evaluation"
        A[Math Expression String] --> B[nodebook-evaluator.ts]
        S[Numeric Scope: Record<string, number>] --> B
        B --> C{mathjs engine}
        C --> D[Result: {value, error}]
    end

    subgraph "Mode 2: Structural Decomposition"
        E[Math Expression String] --> F[equation-to-pn.ts]
        F --> G[mathjs AST Parser]
        G --> H[Recursive AST Walker]
        H --> I[CnlOperation[] Array]
        I --> J[Graph Augmentation]
    end
```

## Internal Implementation

The subsystem is implemented in two primary modules within `packages/nodebook-core/src/`.

### 1. The Evaluation Engine (`nodebook-evaluator.ts`)

This module provides the interface for computing numeric results. It utilizes a sandboxed instance of `mathjs`, which is lazily loaded via dynamic import to optimize initial engine footprint.

*   **`getMathjsInstance()`**: Manages the lifecycle of the `mathjs` instance, ensuring a single shared instance is used across the application.
*    **`evaluateExpression(expression, scope)`**: This is the primary entry point for real-time calculations. It takes an expression string and a `scope` (a mapping of variable names to numbers). The engine handles:
    *   **Standard Numbers**: Returns direct numeric results.
    *   **Complex Objects**: Utilizes `.toNumber()` for mathjs-specific objects (like units or matrices) to ensure compatibility with the graph's numeric attributes.
    *   **Error Handling**: Catches parsing and evaluation errors, returning them as a string within the result object to prevent engine crashes.
*   **`parseExpression(expression)`**: Provides access to the underlying Abstract Syntax Tree (AST), allowing other subsystems to inspect the mathematical structure without executing it.

### 2. The Petri Net Decomposer (`equation-to-pn.ts`)

This module implements a sophisticated transformation algorithm that converts algebraic syntax into a directed graph of transitions and places, effectively representing an equation as a computational flow.

The core logic resides in `walkNode`, a recursive function that traverses the MathJS AST. It maps mathematical constructs to `CnlOperation` types:

*   **`SymbolNode` (Variables)**: Represents an input operand. The engine creates an `addNode` operation to define the variable as a `class`.
*   **`ConstantNode` (Numbers)**: Represents a fixed value. The engine creates a node and uses `addAttribute` to store the numeric value within the graph's attribute registry.
*   **`OperatorNode` (+, -, \*, /, ^)**: Represents a computational transition.
    *   The engine generates a `Function` type node (a Transition).
    *   It creates an output "result" node (a Place).
    *   It establishes `addRelation` operations: input arcs from the operands to the transition (`has prior_state`) and an output arc from the transition to the result (`has post_state`).
    *   The operator's logic is stored in a `definition` attribute.
*   **`FunctionNode` (e.g., `sqrt()`, `pow()`)**: Follows a similar pattern to `OperatorNode`, treating the function name as the transition identifier and its arguments as input arcs.

## Data Structures & Interfaces

### WalkResult Interface
Used during AST traversal to bubble up the state of the decomposition:
*   `placeId`: The ID of the resulting node (the "output" of the current branch).
*   `ops`: An array of `CnlOperation[]` generated by the current subtree.

## Implementation Constraints

*   **Dependency Management**: The system relies on `mathjs`. To maintain a small bundle size, this dependency is loaded dynamically only when a mathematical operation is requested.
*   **Complexity**: The decomposition algorithm is $O(N)$ relative to the number of nodes in the AST, where $N$ is the complexity of the expression.
*   **Determinism**: Node IDs for constants and operators are generated using counters (`opCounter`) and sanitized names to ensure that the same expression always results in the same graph structure.

## Current Behavior vs. Known Gaps

| Feature | Status | Implementation Detail |
| :--- | :--- | :--- |
| **Direct Evaluation** | Complete | Supports all standard arithmetic and mathjs functions. |
| **AST Decomposition** | Complete | Converts expressions into a Petri net-style graph of transitions/places. |
| **Variable Mapping** | Complete | `SymbolNode`s are automatically converted to graph nodes. |
| **Unit Support** | Partial | Evaluates numeric values; unit extraction depends on the scope provided. |
| **Recursive Functions**| Complete | Supports nested operations (e.g., `sin(cos(x))`) via recursive walking. |
| **Symbolic Algebra** | Not Implemented | The engine is strictly numerical or structural, not symbolic. |
